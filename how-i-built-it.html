How I Built a Program and Hosted It on the Internet — With No Technical Experience

Six months ago I couldn't have told you the difference between a repository and a folder. This is the honest story of how I built an interactive HR Analytics Dashboard and put it live on the web — using Claude as my co-builder.

01 · Why

Why I wanted to learn this

I'm an HR professional. My job is people strategy, transformation, and building programmes that actually move the needle for an organisation. I'm not a developer. I never intended to become one.

But something shifted when AI tools started getting genuinely useful. I noticed the people getting the most from them weren't just using AI to write emails faster — they were building things. Dashboards. Tools. Automations. Things that actually changed how work got done.

I didn't want to just talk about AI in HR. I wanted to show what it could do. And the only way to do that credibly was to build something myself.

The specific trigger was a conversation about people analytics. We had all the data — headcount, attrition, salary, engagement scores — sitting in spreadsheets. No one was looking at it in a meaningful way because no one had made it easy to look at.

I wanted to build an HR Analytics Dashboard. Something interactive. Something you could filter by location, drill into attrition, see a gender pay gap breakdown in real time. The kind of thing that usually requires a data team and a six-month project.

I had two things going for me: I understood what good output looked like (that's the HR professional part), and I was willing to try things without fully understanding them first (that's the part I had to learn).

The honest starting point: I understood technology concepts but had never actually built anything. I knew what a dashboard should do — I just had no idea how to make one exist.
02 · Building

How I used Claude to build the thing

The first thing I had to unlearn was the idea that I needed to understand the code before I could use it. I don't understand how my car engine works — that doesn't stop me from driving.

Claude is my co-builder. I tell it what I want in plain English. It writes the code. I review the output, tell it what to change, and we iterate until it looks and works exactly how I imagined.

Here's roughly how the dashboard conversation went:

My prompt to Claude
Build me an interactive HR Analytics Dashboard in React. It should have tabs for: — Headcount overview (total employees, by location, by department) — Attrition analysis (leavers over time, reasons, voluntary vs involuntary) — Gender pay gap breakdown — Salary distribution Use NearForm brand colours: navy #1B2A4A and green #00DC82. The data should come from CSV files with these fields: [EmployeeInfo, EmployeePosition, SalaryInfo] Include a location filter that updates all charts. Make it look professional — not like a template.

That's it. No code. No technical jargon. Just a clear description of what I wanted, what data I had, and what it should look like.

1

Describe the output you want

Be specific about what the thing should do, what it should look like, and what data it needs. The more detail you give, the better the first draft.

2

Review and react, not inspect and fix

You don't need to read the code. Open the output, look at it, and tell Claude what's wrong in plain English. "The chart labels are too small." "The filter doesn't seem to be working." That's enough.

3

Ask Claude to explain anything confusing

When it produced a React component I didn't recognise, I just asked: "What is this and why did you use it?" It explained in plain English. No jargon unless I asked for it.

4

Keep iterating until it's right

My dashboard went through about twelve rounds of feedback before it was where I wanted it. Each round got faster because I got better at describing what I needed.

03 · GitHub

How I added it to GitHub

GitHub is where developers store and share code. Think of it as Google Drive for programs — except it also tracks every change you've ever made, and it connects to tools that can automatically put your code live on the internet.

You don't need to understand how GitHub works deeply. You need to know four things:

1

Create a free account at github.com

Standard sign-up. No payment required for what we're doing.

2

Create a new repository

A repository (or "repo") is just a folder for your project. Click New → give it a name (e.g. hr-analytics-dashboard) → set it to Public → click Create repository.

3

Upload your file

In your new repository, click Add file → Upload files → drag your HTML file in → scroll down and click Commit changes. That's it. Your file is now on GitHub.

4

Your file is now in the cloud

Anyone with the link can see the raw file. But it's not a website yet — that's the next step.

Confused by GitHub? Just ask Claude: "I'm a complete beginner. Walk me through creating a GitHub repository and uploading a single HTML file, step by step, with screenshots." It'll guide you through the exact interface you're looking at.
04 · Vercel

How I hosted it on Vercel

Vercel is a free hosting platform. You connect it to your GitHub repository, and it turns your code into a live website with a real URL you can share with anyone.

This part genuinely surprised me with how simple it is:

1

Sign up at vercel.com

Use your GitHub account to sign in — this is the easiest option because it automatically connects the two platforms.

2

Import your GitHub repository

Click New Project → select your repository from the list → click Deploy. Vercel figures out the rest automatically.

3

Wait about 60 seconds

Vercel builds and deploys your project. When it's done, it gives you a live URL — something like your-project.vercel.app. That's your website, live on the internet.

4

Share the link

Anyone with the URL can access your dashboard. And every time you update the file on GitHub, Vercel automatically re-deploys. You never have to touch Vercel again.

The bit that genuinely made me stop and think: I had just put something on the internet. Not a LinkedIn post. Not a shared Google Doc. An actual piece of software, with its own URL, accessible by anyone in the world. And I did it in an afternoon.

I'm not a developer now. I still don't fully understand what's happening under the hood. But I don't need to — just like I don't need to understand how a spreadsheet calculates a formula to use one.

What I do understand is that the barrier between "I have an idea" and "I have a thing that exists on the internet" is much lower than it used to be. For HR professionals curious about tech, this is the moment to start experimenting.

The only thing stopping most people is starting. Pick something small — a tool, a dashboard, a calculator — describe it clearly to Claude, and see what comes back. The worst that happens is you learn something.
